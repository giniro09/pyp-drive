## マッピング／スキルツリーの方向性

Wayfaringでは、現実の道路構造をそのままゲーム上の世界として扱いたい。

ただし、

- 現実の道路を正しく表現するための構造
- プレイヤーの探索履歴を表現する構造
- ゲーム上の成長を表現する構造

を、すべて同じ粒度で扱う必要はない。

特にスキルツリーについては、すべての交差点を対象にするとノード数が過剰になり、1つ1つのノードの価値や発見感が薄れる可能性が高い。

そのため、以下の3層を分けて考える。

### 1. Road Graph

現実の道路構造そのものを表現する基盤。

ここでは基本的に、実際の走行や交差点判定に必要なすべての交差点・道路を保持する。

ゲーム都合で大幅に間引くのではなく、現実の車両移動を正しく追跡できることを優先する。

Road Graphはゲームロジック全体の土台であり、プレイヤーに必ずしもそのまま見せる必要はない。

### 2. Exploration Map

プレイヤーが実際にどこを走ったかを記録するためのマッピング層。

基本的には、走行した道路や交差点を広く記録する。

細い道路や小さな交差点を走った場合でも、

「実際にそこを探索した」

という履歴は残したい。

Wayfaringでは、

**現実世界での移動が、自分だけの探索済み世界として蓄積されること**

を重要な価値とする。

ただし、内部データとしてすべての道路を保持することと、UI上ですべてを同じ密度で表示することは分けて考える。

例えば、

- ズームアウト時は複数の細かなリンクをまとめて簡略表示
- ズームインすると細かなノードやリンクも表示

など、表示上のLODは別途設計可能。

つまり、

**マッピング対象を減らすのではなく、表示密度を調整する**

方向を基本とする。

### 3. Skill Graph

スキルツリーはRoad Graphそのものではなく、

**Road Graphから一部の重要地点を抽出した、より疎なゲーム用グラフ**

として扱う。

すべての交差点をスキルノードにすると、

- ノード数が増えすぎる
- 新しいノードを発見した価値が薄れる
- スキル画面が過密になる
- どのノードを育てるかという判断が煩雑になる

と考えられる。

そのため、Skill Graphでは一定の条件を満たす交差点のみをスキルノード候補とする。

## スキルノードの抽出

単純に

「信号のある交差点だけ」

と固定するのではなく、

**道路上の重要地点を抽出する**

考え方を採用したい。

信号交差点は有力な条件の一つだが、ゲーム上重要な地点が必ず信号交差点とは限らない。

例えば、

- 信号交差点
- 大きな分岐
- 4方向以上の交差点
- 幹線道路同士の交差点
- 長い道路区間の終端
- Area境界
- 特殊POI周辺
- 地形的に特徴のある地点

などを評価対象とする。

将来的には各交差点にImportance Scoreのような評価値を持たせ、

一定以上の地点だけをSkill Nodeにする方式も検討する。

さらに都市部でノードが密集しすぎないよう、

**Skill Node同士の最低距離**

も持たせたい。

つまり、

信号の有無だけではなく、

**道路構造・周辺環境・ゲーム上の意味・ノード密度**

を組み合わせてSkill Nodeを決める。

## Skill Graphは道路構造に由来するが、道路構造そのものではない

重要なのは、

**Skill Graphの形はRoad Graphに由来するが、Road Graphと完全一致させない**

こと。

例えば現実には、

A → B → C → D → E

という5つの交差点を通る道路でも、

Skill Nodeとして重要なのがA・C・Eだけなら、

Skill Graph上では、

A → C → E

として表現してよい。

内部的にはA-C間でBを通過している情報を保持するが、スキルツリー上では不要な中間ノードを省略する。

これにより、

現実道路に由来する自然な枝分かれ構造を持ちつつ、

ゲームとして理解しやすいスキルツリーにできる。

## スキルツリーそのものを探索対象にする

Skill Nodeは、最初からすべて見えている必要はない。

Wayfaringでは、

**現実世界を探索することで、スキルツリーそのものが発見されていく**

構造にしたい。

例えば、

未訪問時：
- Skill Nodeの存在自体が見えない
- または「何かある」程度の表示

接近・発見時：
- Nodeの存在が判明

到達時：
- Scanner系
- Cargo系
- Roulette系
- Mapping系
- Combat系

など、そのNodeが持つスキル系統が判明する。

その後、Skill Pointなどを使って実際に能力を取得する。

つまり、

**新しい土地へ行くことが、新しい能力系統を発見することにつながる**

設計を目指す。

これによって、

「欲しいスキルがあるから、まだ走っていない方向へ行ってみる」

という、ゲーム側から現実のドライブを生成する動機を作れる。

## スキルポイントの扱い

特定のSkill Nodeを育てるために、そのNode周辺を何度も周回させるような設計は避けたい。

同じ場所を効率的に周回するプレイは、

Wayfaringが目指す

**未知の道へ行くこと**
**探索範囲を広げること**

と逆方向になる可能性がある。

そのため、

- 新規Node発見
- 新規Link走破
- 新Area発見
- 探索実績
- Stake精算
- その他のゲーム活動

などによって得たグローバルなSkill Pointを、発見済みSkill Nodeへ投入する方式を基本候補とする。

現地へ行くことは、

**スキルを発見・解放する条件**

とし、

何度も同じ場所へ通うことは必須にしない。

## 最重要の設計原則

Road Graph、Exploration Map、Skill Graphは同じものではない。

- Road Graph  
  現実世界を正しく扱うための基盤

- Exploration Map  
  プレイヤーが実際に走った世界の記録

- Skill Graph  
  探索によって発見される、疎で意味のある成長ネットワーク

という役割分担にする。

特にSkill Graphでは、

**ノードの数を増やすことより、1つのノードを発見したときの価値を高くすること**

を重視したい。

最終的には、

**現実の道路を走る → 地図が広がる → 新しいSkill Nodeを発見する → 新しい能力を得る → さらに未知の道路へ行きたくなる**

という循環を作ることを目指す。
